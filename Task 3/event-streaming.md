# Архитектурный документ: Потоковая обработка событий AdScale

#### Введение

Данный документ описывает архитектуру потоковой обработки событий для платформы AdScale. Система событий обеспечивает асинхронное взаимодействие между сервисами, инвалидацию кэша, аудит действий и аналитику в реальном времени. В качестве брокера сообщений используется Apache Kafka, выбранный за высокую пропускную способность, долговременное хранение данных и строгие гарантии доставки.

#### 

1. #### Схемы событий

Для описания схем событий используется Apache Avro в связке с Schema Registry. Выбор Avro обусловлен следующими факторами: 

1.Avro позволяет сократить размер полезной нагрузки на 30–50 % по сравнению с JSON за счёт исключения повторяющихся названий полей из каждого сообщения. Это снижает нагрузку на сеть и CPU, обеспечивая необходимый запас производительности для соблюдения SLA ≤80 мс при пиковой нагрузке 18 000 RPS.

* **Проблема JSON:** В JSON названия полей (event\_id, request\_id, creative\_id и т.д.) передаются в каждом сообщении. Это лишний трафик. Если одно событие весит 250 байт, а из них 120 байт — это повторяющиеся названия полей, то 48 % пропускной способности сети тратится впустую.
* **Решение Avro:** Названия полей хранятся только в схеме (в Schema Registry). В поток летят только значения в бинарном виде. Размер сообщения сокращается на 30–50 %.
* **Эффект:** Меньше данных → меньше нагрузка на сеть → быстрее сериализация/десериализация → выигрыш 5–10 мс на каждом событии. Это критично, чтобы уложиться в SLA ≤80 мс.



2\. Использование Avro с Schema Registry гарантирует целостность структуры событий. Строгая валидация схемы на этапе сериализации предотвращает попадание битых данных в поток. Поддержка эволюции схем позволяет внедрять новые метрики (например, антифрод‑сигналы) без остановки или переразвёртывания существующих сервисов.

* Проблема JSON: Слабая типизация. Можно случайно прислать строку вместо числа. Система может «проглотить» ошибку, а потом выдать неверный отчёт.
* Решение Avro: Строгая схема. Если продюсер попытается отправить данные, не соответствующие схеме, библиотека выбросит ошибку ещё до отправки в Kafka. Если потребитель получит данные, не соответствующие схеме, он тоже получит ошибку.
* Эволюция схем: можно безопасно добавлять новые поля (например, fraud\_score или geo\_precision) без поломки старых сервисов. Старые сервисы просто проигнорируют новые поля, новые — будут их использовать.

3\. Использование Avro снижает требования к дисковому пространству кластера Kafka на 30–50 % за счёт компактного бинарного формата. Это напрямую уменьшает стоимость владения инфраструктурой (TCO) и снижает нагрузку на сеть при репликации данных между брокерам

* Проблема JSON: Из‑за избыточности JSON нужно больше дискового пространства в Kafka, чтобы хранить тот же объём событий.
* Решение Avro: Меньший размер сообщений → меньше места на диске → дешевле эксплуатация кластера Kafka.
* Репликация: Меньше данных нужно реплицировать между брокерами Kafka (RF=3). Экономия на трафике внутри дата‑центра.

#### 

#### 2\. Топики Kafka

Система топиков организована по доменному принципу. Каждый домен соответствует бизнес-области или сервису и имеет уникальный префикс. 

Все топики называются по единому правилу:

* Домен — это сервис или бизнес-область, к которой относится событие.
* Тип события — это конкретное действие или группа действий.

Домен кампаний (campaign) :включает топики для событий жизненного цикла рекламных кампаний: создание кампании, изменение её параметров, смена статуса, обновление правил таргетинга и удаление. Эти события являются основой для инвалидации кэша в Auction Service и Dashboard Service.

Домен бюджетов (budget) содержит топики для событий списания и пополнения бюджета кампаний. 

Домен финансов (finance) включает события, связанные с курсами валют, комиссиями, транзакциями и взаиморасчетами. 

Домен дашборда (dashboard) содержит события генерации отчетов, обновления пользовательских сегментов и изменения настроек визуализации. 

Примеры названий:

* campaign.lifecycle — всё про жизнь кампании (создали, изменили, удалили)
* budget.spend — списание денег с бюджета
* dashboard.report\_generated — отчет сформирован и готов к просмотру



##### Партиции

Каждый топик разбит на партиции, которые позволяют разным сервисам читать одновременно сообщение. Количество партиций определяется исходя из ожидаемой нагрузки и требований к порядку обработки. Например: если топик campaign.lifecycle имеет 12 партиций, то 12 экземпляров Auction Service могут обрабатывать события одновременно, каждый свою партицию.

&#x20;Ключом партиции служит идентификатор сущности, к которой относится событие.  Например, у всех событий для кампании cmp\_123 ключ будет campaign\_id = cmp\_123. Kafka вычисляет хеш от ключа и по нему определяет номер партиции: партиция = hash(ключ) % количество\_партиций



|Домен|Префикс топика|Описание|Количество партиций|
|-|-|-|-|
|Кампании|campain|События жизненного цикла кампаний|12|
|Бюджет|budget|Списания и пополнения бюджетов|24|
|Финансы|finance|Курсы валют, комиссии, транзакции|6|
|Дашборд|dashboard|Отчеты, сегменты, настройки|8|
|Аудит|audit|Все события для логирования|10|



#### 4\. Потребители

Потребитель (consumer) — это сервис, который читает сообщения из топика и что-то с ними делает. Например, когда в топик budget.spend попадает сообщение о списании бюджета, Finance Service должен прочитать это сообщение, обновить баланс в базе данных и, возможно, отправить уведомление.

###### Группы потребителей

Несколько потребителей могут объединяться в группу потребителей. Все потребители в одной группе читают разные партиции одного топика. Никто не читает одну и ту же партицию дважды.

Например: если у вас 12 партиций и 3 потребителя в группе, то каждый потребитель возьмет себе по 4 партиции. Если добавить еще 3 потребителя — каждому достанется по 2 партиции.

Главное правило: максимальное количество одновременно работающих потребителей в группе равно количеству партиций. Если партиций 12, то бесполезно запускать 20 потребителей — 8 из них будут простаивать.

###### Пример групп в AdScale:



|название группы|что делает|Потребляемые топики|Количество инстансов|Приоритет|
|-|-|-|-|-|
|auction-service-group|Обновляет кэш для торгов, списывает бюджеты|campaign.lifecycle, budget.spend, budget.topup|12|Критичный|
|dashboard-service-group|Обновляет данные на дашбордах пользователей|campaign.lifecycle, dashboard.report\_generated, dashboard.segment\_update|8|Высокий|
|finance-service-group|Ведет бухгалтерский учет|finance.currency\_rate, finance.transaction, budget.spend|4|Высокий|
|audit-service-group|Сохраняет всё для аудита|audit.all\_events|2|Средний|

Каждый потребитель хранит смещение (offset) — номер последнего прочитанного сообщения в каждой партиции, так потребитель запоминает, что он уже прочитал.

Если потребитель не может обработать сообщение (например, база данных недоступна), он может попробовать снова. В AdScale настроено автоматическое повторение:

* Критические события (бюджеты) — до 3 попыток
* Обычные события (дашборды) — до 5 попыток

Если после всех попыток сообщение так и не обработалось, оно попадает в специальную очередь недоставленных сообщений (Dead Letter Queue). Системный администратор видит, что там появилось сообщение, и может разобраться вручную.

#### 5\. Политика хранения

Kafka не удаляет сообщения после того, как их прочитали. Сообщения хранятся в топике определенное время, даже если все потребители уже прочитали их. 

###### Типы политик хранения

В AdScale используются два подхода: **политика delete** (удаление по времени)

Самый распространенный вариант. Сообщение хранится фиксированное время, после чего удаляется.



|Топик|Срок хранения|Почему именно столько|
|-|-|-|
|campaign.lifecycle|1 день|Достаточно для восстановления после сбоя|
|budget.spend|1 день|Старые данные о списаниях не нужны, они уже в базе|
|dashboard.report\_generated|7 дней|Пользователь может запросить отчет за неделю|
|finance.transaction|90 дней|Требование бухгалтерского учета|



**Политика compact** (компактификация) используется только для топика аудита audit.all\_events. В этом режиме Kafka хранит не все версии сообщений, а только последнее сообщение для каждого ключа.

Пример: для кампании cmp\_123 было 10 изменений статуса. При компактификации останется только последнее — текущий статус кампании. Остальные 9 удалятся, что позволяет экономить место. 

###### Пример

Ситуация: Пользователь через дашборд ставит кампанию на паузу.

Шаг 1: Событие создается

Сервис дашборда создает событие: “Кампания cmp\_123 переведена в статус PAUSED”. Это событие отправляется в топик campaign.lifecycle.

Шаг 2: Событие попадает в партицию

Ключ события — cmp\_123. Kafka вычисляет: hash("cmp\_123") % 12 = 5. Событие попадает в партицию 5.

Шаг 3: Потребители узнают о событии

Одновременно три группы потребителей получают это событие:

* Auction Service (группа auction-service-group): Немедленно удаляет кампанию из кэша ставок. Теперь кампания не участвует в аукционе. Это должно произойти за миллисекунды, иначе деньги будут потрачены зря.
* Dashboard Service (группа dashboard-service-group): Обновляет статус на дашборде пользователя. Пользователь видит, что кампания на паузе. Задержка в пару секунд допустима.
* Audit Service (группа audit-service-group): Сохраняет событие в топик аудита для истории. Это может произойти в течение минуты.

Шаг 4: Событие хранится

В топике campaign.lifecycle событие будет храниться 24 часа. Если какой-то потребитель упал и восстановился через час, он успеет прочитать это событие. Через 24 часа событие автоматически удалится — оно больше никому не нужно, так как все данные уже сохранены в базах данных сервисов.

В топике audit.all\_events это же событие будет храниться вечно в компактифицированном виде. Если позже кампания снова станет активной, последнее событие в аудит-топике будет “статус ACTIVE”, а событие “статус PAUSED” удалится при компактификации.
