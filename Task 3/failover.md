# RPO, RTO, резервное копирование и 12-факторные приложения в архитектуре adScale



#### RPO и RTO

* Auction Service имеет RPO =0 и RTO =1 мин. Это самый критичный сервис, работающий с деньгами в реальном времени. Каждая потерянная ставка — это потерянные деньги рекламодателя. Нулевая потеря данных обеспечивается за счет того, что Kafka выступает источником истины, а in-memory кэш восстанавливается из Kafka при перезапуске. Восстановление за минуту достигается за счет stateless-архитектуры и быстрого прогрева кэша.
* Finance Service имеет RPO =1 мин и RTO= 5 мин. Финансовые транзакции критичны, но короткая задержка в несколько минут приемлема. WAL-логи PostgreSQL архивируются каждую минуту на выделенный сервер хранения. При сбое сервис восстанавливается из последнего полного бекапа с применением WAL-логов, потеря данных не превышает одной минуты.
* Delivery Service — полностью stateless сервис, который не хранит данные. Его RPO=0, а RTO=2 мин. При сбое сервис просто перезапускается, все неотправленные события остаются в Kafka.
* Ad Service и Dashboard Service имеют RPO =5 мин и RTO=30 мин. Настройки кампаний и пользовательские конфигурации не требуют мгновенного восстановления. WAL-логи архивируются каждые пятнадцать минут, полные бекапы делаются каждые шесть часов на выделенный сервер.
* Analytics Service имеет RPO=15 мин и RTO=30 мин. Агрегированные данные и отчеты могут быть пересчитаны, поэтому жесткие требования не нужны. Redis RDB-снапшоты сохраняются каждые пять минут, PostgreSQL бекапы — каждые двенадцать часов.
* Statistics Service имеет самые мягкие требования: RPO=5 мин и RTO=1 час. Сырые события кликов и показов не критичны для бизнеса в реальном времени. ClickHouse FREEZE-снапшоты создаются каждые шесть часов, данные также восстанавливаются из Kafka с ретенцией семь дней.

#### Стратегия резервного копирования

Резервное копирование в AdScale построено по принципу каждый сервис использует свой инструмент с частотой, соответствующей его RPO.

**Для критических сервисов** применяется непрерывное резервирование. Finance Service использует WAL-архивацию PostgreSQL с копированием логов каждую минуту на выделенный сервер хранения. Auction Service полагается на Kafka как на источник истины с ретенцией 24 часа плюс бекапы consumer offsets каждые пять минут. Полные бекапы PostgreSQL для этих сервисов делаются каждые шесть часов.

**Для сервисов со средними требованиями** используются периодические бекапы. PostgreSQL дампы для Dashboard Service создаются каждые шесть часов, инкрементальные копии каждый час. WAL-логи копируются каждые пятнадцать минут. Analytics Service дополнительно сохраняет RDB-снапшоты Redis каждые пять минут для быстрого восстановления кэша отчетов.

Для Ad Server Service хранятся в:

•PostgreSQL — пользователи, сегменты, правила таргетинга, черные списки. Это единственное хранилище, которое нужно восстанавливать.

•Redis — гео-данные, черные списки, сегменты, частотные лимиты. Redis можно перезагрузить из PostgreSQL или пересобрать заново.

•In-memory кэш — не хранит уникальных данных, только копию из Redis и PostgreSQL.

При сбое Redis и in-memory кэш восстанавливаются автоматически при старте сервиса. PostgreSQL восстанавливается из бекапов

**Для некритичных сервисов** бекапы делаются реже. ClickHouse замораживает партиции каждые шесть часов, но основные данные при необходимости восстанавливаются из Kafka за последние семь дней.

**Инфраструктурные компоненты** имеют собственную стратегию. Kafka реплицируется на три узла в разных зонах доступности с ретенцией от 24 часов до 90 дней в зависимости от топика. Consumer offsets бекапятся каждые пять минут в отдельную базу данных. Redis использует AOF (Append Only File) и RDB (Redis DataBase) -снапшоты с автоматическим failover. RabbitMQ сохраняет определения очередей каждые шесть часов, а сообщения сохраняются на диск с зеркалированием очередей.

**Репликация между дата-центрами** обеспечивает географическую избыточность для критичных данных. Finance Service и Kafka offsets реплицируются в удаленный дата-центр каждые шесть часов по выделенному каналу.

Проверка целостности выполняется автоматически: WAL-логи проверяются при каждом копировании, полные дампы тестово восстанавливаются на отдельном сервере раз в сутки, ClickHouse FREEZE-снапшоты верифицируются ежедневно.

#### Соответствие принципам 12-факторных приложений

Кодовая база. У каждого сервиса свой Git-репозиторий, что соответствует принципу одной кодовой базы на сервис.

* Зависимости: все зависимости явно объявлены: Go modules для сервисов на Go, package.json для Node.js, requirements.txt для Python.
* Конфигурация: настройки вынесены в переменные окружения через Kubernetes ConfigMap и Secrets. Ни одного пароля или URL в коде сервиса.
* Внешние сервисы: Базы данных, очереди и кэши подключаются через URL из переменных окружения. Сервис не знает, где именно находится ресурс, что позволяет переключаться между инстансами без изменения кода.
* Сборка, релиз, запуск: Стадии разделены: CI через GitHub Actions собирает Docker-образ, образ пушится в Docker Registry, CD через ArgoCD разворачивает его в Kubernetes.
* Процессы: Каждый сервис запускается как один или несколько процессов в Kubernetes. Auction Service и Delivery Service stateless, что позволяет легко масштабировать их добавлением подов.
* Привязка портов: Каждый сервис слушает на порту, указанном в переменной окружения PORT. Никаких встроенных веб-серверов, только стандартный HTTP сервер языка.
* Параллелизм: Horizontal Pod Autoscaler автоматически масштабирует количество подов на основе нагрузки CPU и лага Kafka. Stateless сервисы масштабируются без ограничений.
* Утилизируемость: Сервисы на Go стартуют менее чем за секунду. Graceful shutdown обрабатывает сигнал SIGTERM: завершаются текущие запросы, коммитятся Kafka offsets, закрываются соединения с базами данных.
* Паритет разработки и продакшна: Тот же Docker-образ используется во всех средах: разработка, стейджинг, продакшн. Отличаются только ConfigMap и объемы ресурсов.
* Логи: Все сервисы пишут логи в stdout в структурированном JSON-формате. Логи собираются через Fluentd и отправляются в централизованную систему хранения.
* Административные процессы: Миграции базы данных выполняются отдельными Kubernetes Jobs перед деплоем новой версии. Одноразовые скрипты запускаются в том же Docker-образе, что и production.



#### Порядок восстановления после аварии

###### Приоритеты восстановления

Приоритет 1: Деньги (Auction + Finance) — остановка влечет за собой прямые убытки

Приоритет 2: Доступность для пользователей (Delivery + Dashboard) — остановка повлияет на потерю доходов

Приоритет 3: Аналитика и отчёты (Statistics + Analytics) — остановка не даст доступа к статистики и аналитике



###### Этапы восстановления:

Этап 1: Определить, какие сервисы недоступны с помощью Мониторинг (Prometheus + Alertmanager), оценить критичность (затронуты ли Auction/Finance) и принять решение: восстанавливать или откатывать

Этап 2: Восстановление критических сервисов (1-5 минут) на примере Auction Service RTO=1 мин

* Kubernetes Health Check обнаружил падение пода-время: 5 секунд
* Kubernetes автоматически перезапускает под - время: 10 секунд
* Новый под загружает in-memory кэш:

&#x20;  - Читает последние offsets из Kafka

&#x20;  - Воспроизводит события из Kafka за последние 24 часа

&#x20;  - Время: 20-40 секунд

* Под начинает принимать трафик-время: 5 секунд

Итого: 40-60 секунд (RTO = 1 минута достигнут)



Если сбой затронул несколько сервисов одновременно, применяется единый порядок:

Шаг 1: Auction Service (1 минута) — восстановить торги

Шаг 2: Finance Service (5 минут) — восстановить списания

Шаг 3: Delivery Service (2 минуты) — восстановить показы

Шаг 4: Dashboard Service (30 минут) — восстановить UI

Шаг 5: Ad Server Service (30 минут) — восстановить таргетинг

Шаг 6: Analytics Service (30 минут) — восстановить отчёты

Шаг 7: Statistics Service (1 час) — восстановить аналитику



#### Ответственность за бюджет

Finance Service — единственный сервис, который может менять баланс кампании. Все остальные сервисы только читают данные из кэша или получают их через API Finance.



|Сервис|Владеет бюджетом|
|-|-|
|Auction Service|Нет<br />чтение кэша, инициирование списывания бюджета|
|Finance Service|Да<br />Единственный сервис, который атомарно проверяет и списывает бюджет|
|Delivery Service|Нет (stateless)|
|Ad Server Service|Нет (сегменты, таргетинг)<br />не работает с бюджетом|
|Statistics Service|Нет (клики, показы)<br />не работает с бюджетом|
|Analytics Service|Нет (отчёты)<br />не работает с бюджетом|
|Dashboard Service|Нет (настройки пользователей)<br />просмотр баланса, инициирование пополнение через Finance|
