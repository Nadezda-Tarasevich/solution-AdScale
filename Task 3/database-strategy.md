# Стратегия данных для сервисов adScale

Для AdScale выбрана стратегия Database-per-Service, что обеспечивает изоляцию сбоев и независимое масштабирование. В данном документе не описана связь сервисов с общими кластерами, такими как Redis и Apache Kafka



|**Сервис**|**Тип базы данных**|**Обоснование**|
|-|-|-|
|Auction Service)|PostgreSQL (выделенный)+ In-Memory Cache для hotpath|PostgreSQL для сервиса ставок нужен для хранения  финансовых операций, которые требуют ACID. Списание бюджета — критическая операция. Никакая NoSQL БД не гарантирует атомарность и изоляцию на уровне PostgreSQL. БД имеет строгую схему данных для хранения информации о ставках, бюджетах кампаний. БД позволяет<br />делать JOIN между таблицами auctions, campaigns и budget\_transactions для формирования отчётов.|
|Сервис кампаний<br />(Ad Server Service)|PostgreSQL (выделенный)<br />Redis (выделенный)<br />|PostgreSQL для сервиса кампаний имеет чёткую реляционную структуру. Кампания принадлежит рекламодателю, имеет бюджет, правила таргетинга, частотные ограничения. Это классическая реляционная модель с ограничениями и ключами. БД позволяет хранить данные в JSON формате, что подходит для хранения правил таргетинга, которые имеют гибкую структуру и меняется в зависимости от DSP партнера.  Ad Server должен быстро найти подходящие кампании для показа рекламы. Это требует JOIN между таблицами  с фильтрацией по определенным условиям.<br />Redis (выделенный): Предоставляет быстрый доступ к гео-данным, чёрным спискам, сегментам пользователей.|
|Сервис статистики<br />(Statistics Service)|ClickHouse+In-Memory (Go)|ClickHouse выбран для Statistics Service  потому что отлично подходит для потоковых write операций, которых будет много тысяч в секунду (клики + показы + результаты аукционов). PostgreSQL не выдержит такой write-нагрузки без шардирования и massive scaling. ClickHouse сжимает данные лучше чем PostgreSQL. Это критично для стоимости хранения и скорости чтения. Так же, статистика нужна для отчётов Dashboard. ClickHouse выполняет агрегации  по миллиардам записей за миллисекунды благодаря колоночному хранению.<br />In-memory (Go) — буфер, который решает основную проблему (скорость записи), не добавляя лишних компонентов в архитектуру. Нужен для хранения временных данных (rate limits, дефолтные ставки) |
|Сервис аналитики<br />(Ananlytics Service)|PostgreSQL (выделенная)<br />Redis (выделенный)|Для сервиса аналитики был выбран PostgreSQL, потому что сервис не хранит миллиард событий, а хранит только агрегированные результаты — маленькие таблицы с готовыми отчётами. Так же PostgrSQL  подходит для высокой частоты запросов и эта БД оптимизирована для UPDATE и INSERT в отличие от  ClickHouse. PostgreSQL имеет строгую консистентность, что позволяет делать точные отчеты, например для финансов.<br />Readis нужен для кэширования популярных отчётов, что бы не перегружать PostgreSQL.<br />|
|Сервис финансов<br />(Finance Service)|PostgreSQL (выделенная инстанция)|PostgreSQL нужен для сервиса финансов для хранение балансов, транзакций, счетов, аудиторского лога, обеспечивает ACID транзакций — атомарное списание + запись аудита, строгую консистентности — никаких “почти правильных” балансов, аудит — каждая копейка должна быть отслежена и десятичные типы для денег (не должно быть округлений).|
|Dashboard сервис|PostgreSQL (выделенная инстанция)|Выделенная PostgreSQL выступает единым источником истины для операционных данных, обеспечивая ACID-транзакции для управления бюджетами и настройками клиентов, сложные реляционные связи между пользователями, дашбордами и виджетами, а также гибкую индексацию для смешанной нагрузки (запись настроек + чтение конфигов).|
