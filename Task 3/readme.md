# Стратегия данных AdScale: Введение



##### Обзор проекта

Данный репозиторий содержит стратегию работы с данными для платформы AdScale — системы управления рекламными кампаниями в реальном времени. Документ описывает архитектурные решения по организации, хранению, масштабированию и обеспечению отказоустойчивости данных в микросервисной среде.

Платформа обрабатывает до 50 000 событий в секунду, управляет бюджетами рекламодателей и требует минимальной задержки при обработке bid-запросов (< 100 мс для критического пути).



##### Основные принципы

Database per Service: Каждый микросервис владеет своей базой данных и отвечает за ее консистентность

CQRS: Разделение команд (запись) и запросов (чтение) для сервисов с разными паттернами нагрузки

Event-Driven: Асинхронное взаимодействие через Kafka для обеспечения слабой связанности

Polyglot Persistence: Выбор типа хранилища под конкретные задачи сервиса



##### БД каждого сервиса

**Сервис ставок (Auction Service)**: Принимает ставки от рекламодателей, определяет победителя аукциона. Это самый нагруженный сервис — до 20 000 запросов в секунду.

Данные хранятся в двух местах:

В памяти сервиса (in-memory) — ставки и бюджеты, которые нужно читать за микросекунды

PostgreSQL — история аукционов для отчетов и аудита

Почему так: Если ставку читать из обычной базы — будет слишком долго. In-memory дает скорость, PostgreSQL дает надежность.

**Сервис кампаний (ad Service)**: Управляет рекламными кампаниями — их создание, настройки, таргетинг.

Решение: PostgreSQL (выделенный)+Redis (выделенный)

Почему: У кампаний сложная структура (кампания → группа объявлений → объявление → креатив). Нужны связи между таблицами и надежные транзакции (чтобы при изменении кампании все данные обновились правильно). Readis Предоставляет быстрый доступ к гео-данным, чёрным спискам, сегментам пользователей.

**Сервис статистики (Statistics Service)**: Собирает события (клики, показы) и записывает их для отчетов.

Решение: ClickHouse.

Почему: ClickHouse создан для записи потоковых данных. Он сжимает данные в 5-10 раз и может вставлять миллионы строк в секунду. PostgreSQL с этим справится хуже.

**Сервис аналитики (Analytics Service):** Строит отчеты, считает метрики, запускает ML-модели.

Решение: PostgreSQL + Redis.

Почему: В PostgreSQL хранятся агрегированные данные. В Redis кэшируются готовые отчеты, чтобы показывать пользователю мгновенно.

**Сервис финансов (Finance Service):** Что делает: Управляет балансами, списывает деньги, выставляет счета.

Решение: PostgreSQL.

Почему: Финансы требуют строгих гарантий: если транзакция началась, она должна завершиться. PostgreSQL обеспечивает ACID (атомарность, согласованность, изоляцию, надежность).



##### Масштабирование базы данных

Масштабирование баз данных необходимо для обеспечения производительности при росте нагрузки и объема данных. В AdScale применяются три подхода:

1\. Репликация Master-Slave — для отказоустойчивости и распределения чтения

2\. Шардирование — для горизонтального масштабирования записи

3\. CQRS — для разделения нагрузки на запись и чтение

Где используем:

•	Auction Service — синхронная репликация (данные копируются мгновенно, задержка минимальная)

•	Finance Service — синхронная репликация (финансы нельзя терять)

•	Campaign Service — асинхронная репликация (копия может отставать на несколько секунд, это допустимо)

Шардирование (разделение данных на части)

Что это: Разбиваем большую базу на несколько маленьких по какому-то признаку.

Как делим в AdScale:

•	Auction Service — делим по campaign\_id (все данные одной кампании на одном сервере)

•	Campaign Service — делим по user\_id (все кампании одного пользователя на одном сервере)

•	Analytics Service — делим по user\_id

Запросы всегда приходят с идентификатором кампании или пользователя. Мы сразу знаем, на каком сервере искать данные.

Read Replicas (копии для чтения)- нужно в Analytics Service, так как отчеты читаются часто и могут быть сложными. Вместо того чтобы нагружать основную базу, читаем с копий. У нас 3 копии для чтения.

CQRS (разделение на запись и чтение) - база для записи данных и база для чтения — разные.

Где используем:

•	Statistics Service: Данные записываются в ClickHouse пачками, а читаются через отдельный интерфейс

•	Analytics Service: Отчеты пишутся в PostgreSQL, а читаются из Redis (кэш)



#### Кэширование

В AdScale применяется двухуровневая архитектура кэша, единая для всех сервисов.

Первый уровень (L1) — это in-memory кэш внутри каждого критического сервиса, реализованный на языке Go. Он расположен на том же хосте, что и под сервиса.

Второй уровень (L2) — это централизованный Redis Cluster, общий для всех сервисов. Он расположен на выделенных узлах.

Redis Cluster состоит из трех Master-нод и соответствующего количества Replica-ноды. Ноды распределены по трём зонам доступности для обеспечения отказоустойчивости.

Распределение данных по Master-нодам:

* Master 1: Данные сервиса аукциона (кампании, бюджеты, default bids)
* Master 2: Данные финансового сервиса (управление редко изменяемыми финансовыми данными, например курс валюты)
* Master 3: Данные сервиса дашборда (сегменты пользователей, счётчики, rate limits)

Каждая Replica-нода находится в другой зоне доступности, чем её Master, и обслуживает запросы на чтение.



###### Инвалидация

В AdScale применяются три механизма инвалидации кэша, каждый из которых используется в зависимости от критичности данных:

1\. По времени (TTL): Самый простой. Запись живет 60 секунд, потом удаляется. Подходит для данных, которые могут устареть.

2\. Удаление при изменении: Когда кампания меняется, отправляется событие в Kafka, и кэш этой кампании удаляется. Следующий запрос загрузит свежие данные.

3\. Синхронное обновление: Для бюджета. Каждое списание сразу обновляет значение в кэше. Даже секунда задержки недопустима.

###### Прогрев кэша (после перезапуска)

Проблема: Когда сервис только запустился, его кэш пуст. Первые запросы будут медленными.

Решение: Сервис загружает самые важные данные (кампании, бюджеты) до того, как начать принимать запросы. Пока загружает — возвращает ошибку 503 (сервис временно недоступен). Это занимает 5-10 секунд. После этого сервис начинает работать, а менее важные данные подгружаются в фоне.



#### Kafka

###### Топики Kafka

Система топиков организована по доменному принципу. Каждый домен соответствует бизнес-области или сервису и имеет уникальный префикс.

Все топики называются по единому правилу:

* Домен — это сервис или бизнес-область, к которой относится событие.
* Тип события — это конкретное действие или группа действий.

Домен кампаний (campaign) :включает топики для событий жизненного цикла рекламных кампаний: создание кампании, изменение её параметров, смена статуса, обновление правил таргетинга и удаление. Эти события являются основой для инвалидации кэша в Auction Service и Dashboard Service.

Домен бюджетов (budget) содержит топики для событий списания и пополнения бюджета кампаний.

Домен финансов (finance) включает события, связанные с курсами валют, комиссиями, транзакциями и взаиморасчетами.

Домен дашборда (dashboard) содержит события генерации отчетов, обновления пользовательских сегментов и изменения настроек визуализации.

Каждый топик разбит на партиции, которые позволяют разным сервисам читать одновременно сообщение. Количество партиций определяется исходя из ожидаемой нагрузки и требований к порядку обработки. Например: если топик campaign.lifecycle имеет 12 партиций, то 12 экземпляров Auction Service могут обрабатывать события одновременно, каждый свою партицию.

&#x20;Ключом партиции служит идентификатор сущности, к которой относится событие.  Например, у всех событий для кампании cmp\_123 ключ будет campaign\_id = cmp\_123. Kafka вычисляет хеш от ключа и по нему определяет номер партиции: партиция = hash(ключ) % количество\_партиций



Для формирования событий для adScale используется Avro — потому что:

* Занимает мало места (в 2-3 раза меньше, чем JSON)
* Работает быстро
* Не дает ошибиться с типами данных

Почему не JSON: JSON в 2-3 раза больше по размеру. При 500 миллионах событий в день это дает экономию \~$32 000 в год.

**Потребители**

Auction Service: Изменения кампаний, списания бюджетов	Чтобы обновить кэш для ставок

Dashboard Service: Изменения кампаний, готовые отчеты	Чтобы показать пользователю

Finance Service: Списания, транзакции	Для бухгалтерии

Audit Service: Всё подряд	Для истории



**Срок хранения событий:**

События кампаний: 24 часа - Достаточно для восстановления после сбоя

События бюджетов: 24 часа - Старые данные не нужны

Отчеты:	7 дней - Пользователь может запросить отчет за неделю

Финансы: 90 дней - Требования бухгалтерии

Аудит: Вечно - Закон требует хранить историю



#### RPO и RTO:

RPO (Recovery Point Objective) показывает, сколько данных мы можем потерять при сбое. RPO равный нулю означает, что не теряется ничего. RTO (Recovery Time Objective) показывает, как быстро сервис должен снова заработать. RTO равный минуте означает, что через минуту после сбоя сервис уже в строю.

В AdScale эти показатели жестко привязаны к тому, насколько сервис критичен для денег.

Критические сервисы: деньги не терпят потерь

* Auction Service имеет RPO равный нулю и RTO равный одной минуте. Это самый нагруженный сервис платформы, обрабатывающий до двадцати тысяч bid-запросов в секунду. Каждая потерянная ставка — это потерянные деньги рекламодателя. Сервис должен восстановиться мгновенно, и ни одно событие не должно пропасть. Достигается это за счет того, что Kafka выступает источником истины с ретенцией 24 часа, а in-memory кэш восстанавливается из Kafka при перезапуске.
* Finance Service имеет RPO равный одной минуте и RTO равный пяти минутам. Финансовые транзакции критичны, но короткая задержка в несколько минут приемлема, если данные не теряются. Резервная копия базы данных с WAL-логами, гарантирует, что потеря составит не более минуты транзакций.
* Delivery Service — stateless сервис, который не хранит данные. Его RPO равен нулю, а RTO — две минуты. При сбое сервис просто перезапускается, и все события, которые он не успел отправить, остаются в Kafka.
* Среднекритичные сервисы: бизнес может подождать
* Ad Service и Dashboard Service имеют RPO пятнадцать минут и RTO тридцать минут. Настройки кампаний и пользовательские конфигурации не настолько критичны, чтобы требовать мгновенного восстановления. Потеря пятнадцати минут изменений — это неприятно, но не катастрофично. Полный бекап PostgreSQL каждые шесть часов с инкрементальными бекапами каждый час позволяет восстановить данные в пределах получаса.
* Analytics Service имеет такие же показатели — RPO пятнадцать минут, RTO тридцать минут. Отчеты и агрегированные данные могут быть пересчитаны, поэтому жесткие требования не нужны.
* Statistics Service имеет самые мягкие требования: RPO один час и RTO четыре часа. Сырые события кликов и показов не критичны для бизнеса в реальном времени. Они могут быть восстановлены из Kafka (ретенция 7 дней) или перезагружены из внешних источников. ClickHouse с бекапами через ALTER TABLE FREEZE каждые шесть часов дает достаточно времени на восстановление.

###### Стратегия резервного копирования

Резервное копирование в AdScale построено по принципу «каждому сервису — свой инструмент». Нет единого решения для всех.

Для критических сервисов используется непрерывное резервирование. Auction Service полагается на Kafka как на источник истины: пока сообщение в Kafka, оно не потеряно. Finance Service использует WAL-архивацию PostgreSQL. Это позволяет восстановиться до любой точки во времени с точностью до минуты.

Для среднекритичных сервисов используются периодические бекапы. PostgreSQL дампы создаются каждые шесть часов, а инкрементальные копии — каждый час. Redis для Analytics Service снимает RDB-снапшоты каждые пять минут, чтобы минимизировать потерю кэшированных отчетов.

Для некритичных сервисов бекапы делаются реже. ClickHouse замораживает партиции каждые шесть часов, но основные данные все равно можно восстановить из Kafka.

Инфраструктурные компоненты — Kafka, Redis Cluster, RabbitMQ — имеют собственную стратегию. Kafka реплицируется на три узла в разных зонах доступности, обеспечивая RPO равный нулю. Redis использует AOF и RDB-снапшоты с автоматическим failover через Sentinel.

###### Соответствие 12-факторным приложениям

Большинство сервисов AdScale следуют принципам 12-факторных приложений, но есть исключения.

**Что соблюдается**: у каждого сервиса свой Git-репозиторий — единая кодовая база. Зависимости явно объявлены: Go modules, package.json, requirements.txt. Конфигурация вынесена в переменные окружения через Kubernetes ConfigMap и Secrets — ни одного пароля или URL в коде. Базы данных подключаются через URL из окружения, что позволяет переключаться между инстансами без пересборки. CI/CD разделяет стадии сборки, релиза и запуска: GitHub Actions собирает Docker-образ, ArgoCD разворачивает его в Kubernetes. Каждый сервис — отдельный процесс, слушающий на порту из переменной $PORT. Автомасштабирование через HPA на основе нагрузки и лага Kafka. Graceful shutdown обрабатывает SIGTERM, завершая текущие запросы и коммитя offsets. Логи пишутся в stdout в JSON-формате и собираются через Fluentd в Loki. Миграции базы данных выполняются отдельными Kubernetes Jobs, а не в коде сервиса. Окружения разработки, стейджинга и продакшна используют одинаковые Docker-образы, отличаясь только конфигурацией.

**Что нарушено:** четыре сервиса хранят состояние, что противоречит принципу «процессы не должны хранить состояние». Finance Service хранит балансы и транзакции в PostgreSQL — это необходимо по определению, финансы не могут быть stateless. Statistics Service использует ClickHouse, который по своей природе является stateful-хранилищем. Временный in-memory кэш Auction Service — это сознательный выбор ради производительности. Redis Cluster как глобальный кэш тоже хранит состояние. Однако это не проблема, потому что:

Stateful сервисы изолированы — только Finance, Statistics и Redis хранят данные. Все остальные сервисы stateless.

Данные восстанавливаемы — in-memory кэш Auction Service перезагружается из Kafka. Redis восстанавливается из AOF или RDB. ClickHouse восстанавливается из бекапов или Kafka.

Горизонтальное масштабирование stateless части — Auction Service, Delivery Service, Dashboard Service легко масштабируются добавлением подов, потому что не хранят состояние.

Stateless сервисы — Auction Service (если не считать in-memory кэш), Delivery Service, частично Dashboard Service — идеально соответствуют 12-факторам. Они быстро запускаются, легко масштабируются и не требуют специального восстановления.

#### Глоссарий:

Креатив — список рекламных объявлений (картинок, видео, текстов), которые прямо сейчас можно показать пользователю в рамках аукциона.

DSP (Demand Side Platform) — «платформа спроса»: система, через которую рекламодатели (или агентства) управляют своими рекламными бюджетами, покупают показы и участвуют в аукционах.

HHTP (HyperText Transfer Protocol) —  протокол передачи данных.

OpenRTB- стандарт (спецификация), который задаёт «общий язык» для всех участников RTB аукциона.

BidRequest - структурированное сообщение в формате OpenRTB, которое содержит всю необходимую информацию

Таргетинг- механизм показа рекламы для выделенной аудитории.

SPOF(Single Point of Failure) — любой компонент системы, поломка которого приводит к остановке всей системы целиком.

RTB(Real Time Bidding) — это «аукцион в реальном времени», который происходит за миллисекунды каждый раз, когда пользователь открывает страницу с рекламой.

БД -база данных

P50/95/99- 50/95/99 % случаев время отклика должно быть не больше этого значения

TTL(time to live)- время, через которое кэш автоматически удалит старую запись.

RPS (request per second)- кол-во запросов в секнду

Read Replica - это копия основной базы данных, которая предназначена только для чтения.

Kafka - это распределённая платформа потоковой обработки данных и брокер сообщений.

SLA (Service Level Agreement) - соглашение об уровне обслуживания

Latency - задержка

WAL- (Write-Ahead Log) — это механизм, используемый базами данных (в первую очередь PostgreSQL) для обеспечения надежности данных. Название переводится как «журнал упреждающей записи».

AOF - Appen only file

RDB - ReadisDatabase

RPO (Recovery Point Objective) — сколько данных мы можем потерять при сбое. Измеряется во времени. RPO = 0 значит, что мы не теряем ничего.

RTO (Recovery Time Objective) — как быстро сервис должен снова заработать после сбоя. RTO = 1 минута значит, что через минуту после сбоя сервис уже работает.
