# Проектирование RTB-сервиса и интеграции с DSP:Введение

#### 

#### Обзор проекта

Данный проект посвящён проектированию архитектуры критичного компонента — RTB-сервиса (Real-Time Bidding) для интеграции AdScale с новой DSP-площадкой. Основная цель — обеспечить соблюдение жёстких требований по времени отклика (P95 latency < 80 ms) и надёжности (SLA 99.9%) при росте трафика до 18 000 RPS (до 50 000 RPS через год).

#### 

#### Контекст

AdScale — платформа для автоматизированной закупки рекламы в реальном времени. Компания получила предложение об интеграции с крупной DSP-площадкой, что создаёт серьёзные технические вызовы:

* Рост трафика: +20% немедленно (до 18 000 RPS), двукратный рост через год (до 50 000 RPS)
* Жёсткие SLA: время ответа не более 80 ms, штрафы за деградацию времени отклика и простои
* Текущее состояние: монолитная архитектура, работающая на пределе (P95 latency 110–120 ms при требовании ≤ 100 ms)

###### Цели

1\. Выделить сервис ставок (Auction Service) из монолита с чёткими границами, API, зависимостями и моделью данных

2\. Спроектировать взаимодействие между компонентами с обоснованием выбора протоколов (gRPC, REST, Kafka)

3\. Разработать API Gateway для DSP-интеграции с rate limiting, аутентификацией, circuit breaker и мониторингом

4\. Обеспечить надёжность через паттерны Circuit Breaker, Retry with Backoff, Idempotency и Fallback



#### Архитектурные решения



|**Решение**|**Выбор**|**Обоснование**|
|-|-|-|
|Внешний протокол (DSP)|REST/HTTPS (OpenRTB)|Промышленный стандарт, совместимость со всеми DSP|
|Внутренний протокол (Bidding)|gRPC (protobuf)|Минимальная latency (1-3 ms), строгая типизация|
|Протокол для событий|Kafka|Высокая пропускная способность, гарантированная доставка, replay|
|Протокол для событий|Kong|Встроенные rate limiting, circuit breaker, JWT auth, Prometheus метрики|
|База данных Auction|PostgreSQL + In-Memory Cache|In-Memory для hot path, PostgreSQL для персистентности|
|Circuit Breaker|Встроенный в API Gateway|Защита Ad Server от каскадных сбоев|
|Идемпотентность|Уникальные ключи + таблица idempotency\_keys|Ни одного двойного списания|



#### Краткое описание ключевых компонентов

###### 1\. Сервис ставок (Auction Service)

Выделенный микросервис для взвешивания ставок, применения бизнес-правил и определения победителя аукциона.

Ключевые характеристики:

* Язык: Go (высокая производительность, конкурентность)
* In-Memory Cache: ставки, бюджеты, кампании (latency < 0.01 ms)
* PostgreSQL: история аукционов, аудит бюджета, ключи идемпотентности
* Событийная связь с Finance: асинхронное обновление бюджетов через Kafka

Основные API:

* PlaceBid() — gRPC, синхронный, вызывается Ad Server
* GetAuctionStatus() — gRPC, синхронный
* AuctionResultEvent — Kafka, асинхронный (публикуется)
* BudgetChangedEvent — Kafka, асинхронный (потребляется от Finance)

###### 

###### 2\. API Gateway (Kong)

Единая точка входа для всех DSP-партнёров с встроенными механизмами защиты и мониторинга.

Ключевые функции:

* Rate Limiting: до 2000 RPS на одного DSP, динамическое увеличение лимитов
* Аутентификация: JWT (HS256), проверка API-ключей
* Circuit Breaker: защита Ad Server от каскадных сбоев (50% ошибок → OPEN)
* Мониторинг: Prometheus метрики, алерты на P95 latency > 80 ms
* Fallback: кэшированные или дефолтные ставки при недоступности backend

###### 

###### 3\. Паттерны надёжности



* Circuit Breaker (API Gateway → Ad Server): Блокировка вызовов при > 50% ошибок, 30 сек таймаут
* Retry with Backoff (Kafka Producer): 3 попытки с экспоненциальной задержкой, jitter 50%
* Idempotency (Списание бюджета в Auction): Уникальный ключ для каждой финансовой операции
* Fallback (Все внешние вызовы):In-Memory → Redis → Default Bid (безопасный проигрыш)



###### 4\. Протоколы взаимодействия

Внешнее (DSP → Gateway): REST/HTTPS (OpenRTB 2.x/3.0)

Внутреннее (Gateway → Ad Server): gRPC (protobuf)

Внутреннее (Ad Server → Auction): gRPC (protobuf)

Внутреннее (Auction → Delivery): gRPC (protobuf)

Асинхронные события: Kafka (Avro)

Global Cache: Redis Protocol

###### 7\. Глоссарий:

Креатив — список рекламных объявлений (картинок, видео, текстов), которые прямо сейчас можно показать пользователю в рамках аукциона.

DSP (Demand Side Platform) — «платформа спроса»: система, через которую рекламодатели (или агентства) управляют своими рекламными бюджетами, покупают показы и участвуют в аукционах.

HHTP (HyperText Transfer Protocol) —  протокол передачи данных.

OpenRTB- стандарт (спецификация), который задаёт «общий язык» для всех участников RTB аукциона.

BidRequest - структурированное сообщение в формате OpenRTB, которое содержит всю необходимую информацию

Таргетинг- механизм показа рекламы для выделенной аудитории.

SPOF(Single Point of Failure) — любой компонент системы, поломка которого приводит к остановке всей системы целиком.

RTB(Real Time Bidding) — это «аукцион в реальном времени», который происходит за миллисекунды каждый раз, когда пользователь открывает страницу с рекламой.

БД -база данных

P50/95/99- 50/95/99 % случаев время отклика должно быть не больше этого значения

TTL(time to live)- время, через которое кэш автоматически удалит старую запись.

RPS (request per second)- кол-во запросов в секнду

Read Replica - это копия основной базы данных, которая предназначена только для чтения.

Kafka - это распределённая платформа потоковой обработки данных и брокер сообщений.

SLA (Service Level Agreement) - соглашение об уровне обслуживания

Latency - задержка
