# Проектирование API Gateway для DSP-интеграции

#### 1\. Маршрутизация запросов на ставки

API-слой должен обеспечивать единую точку входа для всех DSP-партнёров и маршрутизировать запросы к соответствующим внутренним сервисам.

Все DSP-партнёры отправляют bid requests на единый URL-адрес, который обслуживается API Gateway. Gateway анализирует путь запроса (openrtb/2.x/bid/ или openrtb/3/0/bid) и направляет его в нужный внутренний сервис: Ad Server Service. Для совместимости с OpenRTB (JSON) и внутренней реализацией сервиса (gRPC) предусмотрен слой преобразования протоколов.

###### Правила маршрутизации:

* **Метод**: POST
* **Таймаут соединения**: 1 секунда - быстрый отказ при недоступности backend
* **Таймаут чтения/записи**: 3 секунды - укладывается в SLA 80 ms
* **Повторные попытки**: 0- bidding не терпит задержек — лучше вернуть проигрыш
* **Размер payload**: max 10 KB - Защита от слишком больших запросов

###### Обработка запроса в Gateway:

При получении запроса от DSP Gateway выполняет следующие шаги:

* Проверяет, что метод запроса — POST
* Проверяет Content-Type — только application/json
* Проверяет размер payload — не более 10 KB
* Проверяет наличие обязательных полей OpenRTB (ID запроса, хотя бы одна импрессия)
* Если валидация пройдена — передаёт запрос в Ad Server Service через gRPC
* Если валидация не пройдена — возвращает ошибку 400 Bad Request



#### 2.Ограничение частоты запросов (Rate Limiting)

DSP‑партнёр не должен слать 50 000 RPS, если договорился на 18 000. Если он начнёт «бомбить» запросами, система упадёт.

Rate limiting защищает внутренние сервисы от перегрузки, если один из DSP-партнёров начинает отправлять слишком много запросов. Требование от DSP: 18 000 RPS + 20%

###### Стратегия rate limiting:

* rate-limit-per-minute: 2000 запрсов – обеспечивает защиту от пиковых нагрузок и DDoS, cтандартный лимит для одного DSP
* rate-limit-per-hour: 100000 запросов - балансировка долгосрочной нагрузки. Сглаживает неравномерность трафика внутри часа (например, высокие пики в начале часа), позволяя DSP работать с комфортным запасом, но исключая злоупотребление ресурсами при нормальной средней скорости (\~1 667 запросов в минуту).
* rate-limit-per-day: 2 млн запросов - предотвращение злоупотреблений и гарантия ёмкости. Обеспечивает максимальный дневной объем, достаточный для 99% типовых кейсов (например, в реальной торговле RTB или мониторинге ставок). Предотвращает монополизацию дневного лимита системы одним DSP, оставляя ресурсы для других партнёров.



При превышении лимита, возвращать  HTTP 429 Too Many Requests до того, как запрос дойдёт до бэкенда. Бэкенд даже не должен знать, что его хотели атаковать.



###### Информирование DSP о лимитах:

При каждом ответе Gateway возвращает DSP-партнёру заголовки с информацией о текущем состоянии rate limit:

* Максимальное количество запросов в минуту
* Сколько запросов осталось
* Через сколько секунд счётчик сбросится



#### 3\. Аутентификация

Каждый DSP-партнёр получает уникальные учётные данные при регистрации и использует их для аутентификации каждого запроса.  Для RTB‑интеграций стандарт — это HMAC или mTLS.

Вариант А (HMAC): DSP подписывает тело запроса секретным ключом. Шлюз проверяет подпись. Если не совпадает — 401 Unauthorized.

Вариант Б (mTLS): У каждого партнёра есть свой SSL‑сертификат. Шлюз принимает запросы только от обладателей валидных сертификатов. Это «золотой стандарт» для финансовых и рекламных интеграций.

Аутентификация входящих запросов от DSP‑партнёра реализована через механизм mTLS (Mutual TLS). API Gateway проверяет валидность клиентского сертификата. Запросы без валидного сертификата отклоняются на уровне шлюза, не попадая во внутреннюю сеть.



#### 4\. Паттерн автоматического размыкателя (Circuit Breaker)

Для защиты от каскадных отказов в API Gateway реализован паттерн Circuit Breaker. Каждый DSP-партнёр имеет свой собственный Circuit Breaker. Таким образом, если один DSP перегружает систему, это не влияет на других партнёров.

При превышении порога ошибок (более 5 ошибок подряд или 50 % неудачных запросов за 1 минуту) шлюз переходит в состояние “Open” и прекращает маршрутизацию запросов в сервис ставок. Вместо этого возвращается ответ 503 Service Unavailable или 200 OK с флагом no\_bid=true. Это предотвращает перегрузку сервиса и позволяет системе быстро восстановиться. Через 30 секунд шлюз автоматически проверяет доступность сервиса (Half-Open).

###### Используем классическую модель состояний (паттерн Circuit Breaker):

* Closed (Замкнут): Нормальное состояние. Сервис работает стабильно, пропускать запросы к backend.
* Open (Разомкнут): Сервис деградирует. Более 50% ошибок за последние 60 секунд. Шлюз перестаёт слать запросы в сервис. Вместо этого он сразу возвращает клиенту ответ (например, 503 Service Unavailable или 200 OK с флагом no\_bid=true, чтобы площадка могла спросить другого участника аукциона).
* Half-Open (Полуоткрыт): Проверка. Прошло 30 секунд после размыкания. Если он успешен — возвращаемся в состояние Closed. Если нет — снова Open.



#### 5\. Мониторинг времени отклика (Latency Monitoring)

AdScale обязана соблюдать SLA по времени отклика: P95 latency не более 80 ms. Мониторинг позволяет отслеживать соблюдение SLA и своевременно реагировать на деградацию. В инструменты мониторинга входит настройки: метрик, алерты, дашборды. 

Необходимые метрики для API Gateway в рамках adScale:

* Request Time: Общее время обработки запроса (от получения запроса до отправки ответа).
* Upstream Time: Время, которое запрос провёл в бэкенде (в bidding-service).
* SSL Handshake Time: Время установки HTTPS‑соединения.
* Response Time: Время передачи ответа клиенту.

**Какие метрики собирать:** 

* P95 latency: Время, за которое обрабатываются 95 % запросов. Это ключевой показатель для SLA. 
* Error Rate: Процент запросов с ошибками (4xx, 5xx). 
* Rate Limit Rejections: Сколько запросов было отклонено из‑за лимитов. 
* Circuit Breaker State: В каком состоянии сейчас шлюз (Closed/Open/Half-Open).
