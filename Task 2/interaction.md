# Протоколы и паттерны взаимодействия в микросервисной архитектуре adScale



#### Выбор между REST и gRPC  для внутреннего инфопотока.

Для внутреннего взаимодействия, особенно между Ad Server и Auction Service, предпочтительней использовать gRPC, так как он обеспечивает минимальную задержку и низкую сетевую нагрузку. Ожидается выигрыш 10–15 мс по сравнению с REST, что критично для укладывания в SLA ≤80 мс.  Можно было бы выбрать  и REST и уложиться в  80 ms. Но проблема в том, что 80 ms — это P95. А P99 может быть 150-200 ms. gRPC даёт запас прочности, который позволит  выдерживать SLA при пиковых нагрузках.

#### Протокол для внешней интеграции с DSP. 

Протокол: OpenRTB (JSON over HTTP)- это отраслевой стандарт, обеспечивающий совместимость со всеми DSP‑платформами на рынке и позволяет использовать готовые библиотеки для валидации входящих запросов. Если adScale предложит партнерам gRPC — его просто не подключат. Поэтому выбор REST для внешнего протокола — это не техническое, а бизнес-решени

#### 

#### REST для Campaign Service (кампании, правила, бюджеты)

Операции с кампаниями (создание, редактирование, чтение правил) происходят редко и не влияют на скорость аукциона. Здесь важнее удобство разработки и отладки.

Для Campaign Service выбран REST API. Операции изменения кампаний и правил происходят вне критического пути RTB. Приоритетом здесь является удобство разработки, отладки и интеграции с UI кабинета рекламодателя. JSON‑формат упрощает тестирование и документирование API. Так как REST — это стандарт индустрии и HTTP отлично кэшируется.



#### Для потоковой обработки событий — Kafka

Запись статистики (клики, показы) не должна блокировать аукцион. 

Для обработки событий кликов и показов используется асинхронный подход на базе Apache Kafka, что позволяет сервису ставок немедленно вернуть ответ площадке, не дожидаясь записи в базу данных. События накапливаются в очереди и обрабатываются фоновыми консьюмерами. Без Kafka пришлось бы или терять события (что недопустимо для биллинга), или переплачивать за инфраструктуру, способную обрабатывать пиковые нагрузки.

Kafka решает три ключевые проблемы:

* Буферизация — если Statistics Service временно недоступен, события не теряются
* Пиковая нагрузка — Kafka может принять 1 млн событий/сек, даже если потребители не успевают
* Replay — если  обнаружена ошибка в агрегации, можно пересчитать статистику за последние 24 часа

#### Выбор API Gateway 

API Gateway нужен AdScale для решения конкретных проблем: защита от перегрузки DSP, единая аутентификация, мониторинг SLA, безопасное внедрение новых версий и снижение операционной нагрузки на команду из 35 человек. Без Gateway команда потратила бы значительное время на реализацию rate limiting, circuit breaker и аутентификации в каждом из семи сервисов — вместо того чтобы один раз настроить это в API Gateway и сосредоточиться на бизнес-логике.

Ниже сравнительная таблица позволяющая оценить преимущества Kong и NGINX:

|**Сценарий**|**Kong**|**NGINX**|
|-|-|-|
|Rate limiting DSP (2000 RPS)|Встроенный, с Redis|Требует Lua + Redis|
|gRPC проксирование (Auction)|Нативная поддержка|Требует NGINX Plus|
|Circuit Breaker (защита Auction)|Встроенный плагин|Нужно писать с нуля|
|JWT аутентификация DSP|Встроенный плагин|Требует Lua|
|Мониторинг latency (Prometheus)|Встроенные метрики|Требует модуль vts|
|Canary deployment (новый DSP)|Встроенный плагин|Требует Lua|
|Динамическое управление (Admin API)|REST API|Только nginx.conf|



Kong лучше подходит для AdScale, потому что он предоставляет все необходимые функции (rate limiting, gRPC, circuit breaker, JWT, Prometheus метрики, Admin API) «из коробки», не требуя кастомной разработки на Lua. Для команды без выделенного SRE это означает быстрое внедрение (1-2 недели), низкую стоимость поддержки и минимальный риск ошибок. NGINX потребовал бы написания кастомных модулей, найма специалиста по Lua и более длительного внедрения — что нереалистично для AdScale с ограниченным бюджетом и сжатыми сроками.
