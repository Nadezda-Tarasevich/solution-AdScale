### ADR‑002. Выделение сервиса ставок в качестве первого приоритета

#### Контекст



Компания AdScale ожидает рост трафика на 20% (до \~18 000 RPS) в ближайшие 3 месяца и двукратный рост через 1 год (до \~50 000 RPS) связанное с подключением новой DSP-площадки с жёсткими SLA: P95 latency не более 80 мс и штрафы за деградацию и простои.

В рамках ADR рассматривается предложение выделить движок ставок (Bidding Engine) в отдельный независимый сервис на языке Go. Трафик ставок будет маршрутизироваться через API Gateway на этот новый сервис, в то время как остальные функции (статистика, кабинет) останутся в монолите.



###### Текущее состояние системы:

* Монолитная архитектура, работающая на пределе (15 000 RPS в пике)
* P95 времени отклика: 110–120 мс (требование не более 100 мс)
* Периодические деградации в часы пик
* Отсутствие запаса по производительности
* Нет выделенных SRE, документации, контейнеризации, очередей и кэша

###### Ключевая проблема:

Самый критичный по latency компонент — Auction Engine (сервис ставок). Он:

* Принимает HTTP-запросы от рекламного сервера
* Применяет бизнес-правила для взвешивания ставок
* Определяет победителя аукциона
* Использует синхронные вызовы к базе данных (PostgreSQL)
* Наиболее чувствителен к любым задержкам

При текущей архитектуре рост трафика приведёт к:

* Деградации времени отклика свыше 150 мс
* Сбоям в работе модуля ставок
* Проигрышу аукционов
* Финансовым штрафам от DSP-партнёра
* Репутационным потерям
* Невозможности обслуживать текущих клиентов



#### Рассмотренные альтернативы



###### Альтернатива 1: Сервис статистики как первый приоритет

Сервис имеет непосредственное подключение к базе данных для записи событий, наличие прямой записи без буферизации.

**Плюсы:**

* Меньше бизнес-логики, проще в реализации
* Даёт быстрое снижение нагрузки на запись в БД (60–80%)
* Меньше рисков для целостности данных

**Минусы**:

* Не решает проблему latency аукционов — основную угрозу для SLA
* Снижение нагрузки на БД не гарантирует улучшение времени отклика Auction Engine
* Бизнес-ценность ниже: статистика терпима к задержкам, аукцион — нет



###### Альтернатива 2: Финансовый сервис как первый приоритет

Сервис связан с базой данных, используется синхронный доступ для проведения транзакций.

**Плюсы**:

* Критичен для бизнеса (деньги)
* Часто используется другими модулями

**Минусы**:

* Очень сильная связанность с другими модулями
* Высокий риск ошибок при выделении
* Не влияет напрямую на latency аукционов



###### Альтернатива 3: Изоляция аналитики как первый шаг

Сервис использует прямые SQL-запросы к базе данных, нагрузка на аналитические запросы ведёт к блокировкам и росту latency.

**Плюсы**:

* Быстрое улучшение (2–3 дня)
* Снимает конкуренцию за БД со стороны тяжёлых запросов

**Минусы**:

* Это не выделение модуля, а инфраструктурное улучшение
* Не решает проблему самого Auction Engine
* Должно быть сделано в любом случае, но не как первый приоритет миграции



#### Решение

Выделить сервис ставок в качестве первого приоритета.

###### Обоснование:

1\. Прямое влияние на SLA: сервис ставок — самый критичный компонент по latency. Любая задержка здесь напрямую ведёт к таймаутам, штрафам и партнеров DSP.

2\. Максимальная бизнес-ценность: улучшение времени ответа аукционов с текущих 110–120 мс до <80 мс — это ключевой бизнес-результат, ради которого затевается вся миграция.

3\. Снижение технического долга в самом проблемном месте: текущий движок сервиса ставок использует синхронные вызовы к БД, имеет жёсткие связи с финансовым модулем и рекламным сервером. Выделение в отдельный сервис заставит спроектировать чистые интерфейсы.

4\. Подготовка к масштабированию: если сервис ставок станет микросервисом, его можно будет горизонтально масштабировать, кэшировать данные о ставках и бюджетах и оптимизировать алгоритмы без влияния на другие компоненты.

5\. Фокус на корень проблемы: все остальные проблемы (нагрузка на запись, конкуренция за БД) — вторичны по сравнению с тем, что сервис ставок не успевает обрабатывать запросы вовремя.

###### Риски:



* Ошибки в логике ставок (финансовые потери): выход-> параллельный запуск старого и нового сервисов, сравнение результатов перед переключением
* Увеличение latency из-за сетевых вызовов: выход-> сервис ставок будет размещён в том же дата-центре/кластере, что и монолит; использование in-memory кэша для снижения обращений к БД
* Команда не успевает за 3 месяца: выход-> предлагается запуск сначала MVP (только критический путь без всех оптимизаций), затем итеративные улучшения



###### Последствия

**Положительные**

* Прямое влияние на ключевую бизнес-метрику (latency)
* Возможность горизонтального масштабирования самого нагруженного компонента
* Чёткая граница между Auction Engine и остальной системой
* Готовность к будущему росту (50 000 RPS)

**Отрицательные**

* Первый микросервис — самый сложный (больше всего бизнес-логики)
* Требуется тщательное тестирование и с параллелизацией работы нового сервиса со старым
* Высокие требования к команде: нужно спроектировать интерфейсы, которые не придётся переделывать

**Компромиссы**

* Сервис статистики (Event Writer) будет выделен вторым приоритетом после сервиса ставок
* Read Replica для аналитики будет поднята параллельно как инфраструктурное улучшение (независимая задача)
* Финансовый сервис останется в монолите до следующего квартала
