# Функциональные требования к системе AdScale в результате интеграции с DSP– партнером



#### Функциональные требования



1. Система должна принимать HTTP запросы типа BidRequest от DSP партнёра в формате спецификации OpenRTB  (по версии, согласованной с партнёром). Каждый входящий запрос должен проходить автоматическую валидацию схемы и проверку токенов аутентификации.
2. Для каждого валидного BidRequest система должна сформировать и вернуть ответ типа BidResponse в течение ≤80 мс (P95). В ответе должна быть указана ставка цена, идентификатор креатива и ссылка для трекинга.
3. В BidResponse система должна включать дополнительные параметры трекинга (device ID, IP адрес, timestamp), требуемые DSP партнёром для их внутренней аналитики.
4. При обработке BidRequest система должна иметь механизм автоматического отключения (circuit breaking) для медленных или упавших внешних компонентов (например, сервиса статистики или медленной реплики БД). Если зависимость не отвечает за заданный таймаут, система должна «отрезать» её, вернуть дефолтный ответ или пропустить шаг, но не блокировать весь аукцион.
5. При обработке запроса система должна динамически формировать список доступных креативов на основе правил таргетинга (гео, устройство, демография), статуса кампании (активна/пауза), остатка бюджета и частоты показов. Из этого списка должен быть выбран победитель по правилам аукциона.
6. Факт показа рекламы и клика должен фиксироваться системой без блокировки критического пути обработки аукциона. События должны помещаться в очередь сообщений и обрабатываться фоновым процессом.
7. Система должна гарантировать, что каждое событие (клик/показ) будет учтено ровно один раз, даже при сбоях сети или перезагрузке сервисов. Должен быть реализован механизм идемпотентности.
8. Система должна иметь возможность гибкой настройки таргетинга на основе данных от DSP, включая поведенческие, демографические и прочие сегменты аудитории.
9. Система должна поддерживать динамическую загрузку и применение правил, специфичных для данного DSP (например, «не участвовать в аукционах на доменах из чёрного списка партнёра», «приоритет определённых категорий креативов»). Эти правила должны обновляться без деплоя кода.
10. Система должна  уметь предоставлять подробные отчёты по эффективности кампаний, включая информацию о ставках, выигранных показах и аналитику поведения пользователей.
11. Система должна собирать метрики latency (время обработки запроса) с разбивкой по перцентилям (P50, P95, P99) для каждого типа запросов (Bid Request, трекинг события). Должны быть настроены автоматические алерты (в Telegram/Max/на почту команде) при превышении порога P95 > 75 мс (запас 5 мс до SLA) или росте ошибок выше 0,1 %.

#### Технические требования



1. Каждый экземпляр сервиса (или монолит в целом) должен предоставлять эндпоинт /health с тремя статусами: OK, Degraded, Critical. Балансировщик нагрузки должен уметь исключать из ротации экземпляры в статусе Degraded или Critical, чтобы не слать им новые запросы.
2. При высокой нагрузке или частичных сбоях система должна уметь осознанно отключать «некритичные» функции (например, расширенную аналитику в реальном времени, детальную валидацию вторичных полей), чтобы сохранить работоспособность ядра (приём ставок, выбор креатива, возврат ответа ≤80 мс).
3. Каждый входящий запрос должен получать уникальный идентификатор, который пробрасывается через все компоненты системы и фиксироваться в логах. Должна быть возможность по одному идентификатору запроса восстановить полный путь запроса: какие компоненты его обрабатывали, сколько времени занял каждый этап, где возникла задержка.
4. Внедрить Read Replica для аналитических запросов; все тяжёлые отчёты и выборки должны идти только на реплику. Основная (primary) БД используется только для транзакций RTB и финансовых операций.
5. Запись событий в БД должна происходить через промежуточный буфер (message queue). Время помещения события в очередь ≤ 5 мс. Гарантированная доставка (at least once) и дедупликация по уникальному идентификатору события.
6. Должны быть настроены регулярные бэкапы базы данных (минимум ежечасные инкрементальные + ежедневные полные) с проверкой возможности восстановления. Должен быть задокументированный план Disaster Recovery (DR) с целевыми показателями: RPO (Recovery Point Objective) ≤15 минут (допустимая потеря данных) и RTO (Recovery Time Objective) ≤60 минут (время восстановления).
7. Внедрить слой кэширования (Redis). Время ответа на кэш запрос ≤ 1 мс. TTL (время жизни) кэша настраивается для каждого типа данных (правила кампаний — 5–15 мин, списки креативов — 1–5 мин).
8. Устранить единую точку отказа (SPOF) на уровне инфраструктуры и БД. Развёртывание второго production кластера (hot standby) или использование мульти зонной архитектуры. Репликация БД (синхронная или полусинхронная). Автоматический failover ≤ 60 секунд.



#### Бизнес ограничения

##### Бюджет и стоимость инфраструктуры

Компания не готова выделять бюджет на масштабную миграцию в облако или покупку большого количества новых серверов в ближайший квартал. Решение должно быть экономически обоснованным: приоритет — оптимизация текущей инфраструктуры и использование уже имеющихся ресурсов.

Как это влияет на архитектуру: Сначала внедряем Redis для кэширования и Kafka для буферизации статистики — это даст быстрый эффект по latency без больших затрат на железо. Декомпозицию монолита делаем поэтапно, начиная с самых нагруженных частей.

##### 

##### Сроки и дедлайны

Интеграция с DSP партнёром должна быть завершена и протестирована в течение 6 недель. Критические SLA (≤80 мс) должны соблюдаться уже через 2 недели после начала интеграции».

Используем промежуточные решения, которые дают быстрый эффект:

* Внедряем кэш (Redis) — это можно сделать за 1–2 недели.
* Выносим запись статистики в очередь (Kafka) — это снимает блокировки и сразу улучшает latency.

##### 

##### Кадровые ограничения

В штате нет выделенного SRE инженера. Поддержка и эксплуатация будут осуществляться текущей командой бэкенд разработчиков (35 человек, но без экспертизы в SRE). Нет технического писателя, документация не ведётся.

Влияние на архитектуру:

* должны использоваться понятные и поддерживаемые технологии в рамках знаний команды разработки.
* минимум ручной настройки, понятные логи, простые скрипты деплоя.
* использование простых механизмов масштабирования.

##### 

##### Стратегические решения и внешние факторы (Политика компании)

Компания обязана хранить все персональные данные и данные о ставках на серверах в юрисдикции РФ (on premise). Использование публичных облаков (AWS, GCP, Azure) для хранения основных данных запрещено».

Влияние на архитектуру:

* Все компоненты (Kafka, Redis, PostgreSQL) должны быть развёрнуты на собственной инфраструктуре (on premise). Нужно предусмотреть план резервного копирования и восстановления на своих серверах
